Шаг 1: Модель данных (DOD-подход к векторам)
Обычный программист создал бы класс Vector с полями id, text и float_array, а потом запихал бы их в std::vector<Vector>. Для кэша процессора это смерть.
Ты делаешь разделение (как в ECS): отдельно лежат геометрические данные, отдельно текстовые метаданные.

* Что писать в коде:
Создай структуру, где все координаты векторов лежат в одном гигантском непрерывном массиве. Допустим, размерность одного вектора эмбеддинга (выдавать его будет нейронка) равна 384 (стандарт для легковесных моделей типа all-MiniLM-L6-v2).
struct VectorStorage {
    std::vector<float> all_dimensions; // Монолитный массив. Размер = Количество векторов * 384
    std::vector<std::string> raw_texts; // Тексты лежат отдельно, чтобы не портить кэш-линии
    std::vector<uint32_t> access_counters; // Сколько раз к вектору обращались (нужно для фильтра)
    
    size_t vector_count = 0;
    const size_t dim = 384;
};
Почему это круто: Когда процессор будет считать косинусное сходство, он будет линейно читать массив all_dimensions. Благодаря кэш-локальности, процессор будет заранее подгружать числа в L1/L2 кэш, и скорость будет космической.
Шаг 2: Многопоточный движок вычислений (По Уильямсу)
Тебе нужно написать простой пул потоков (ThreadPool). Его задача — взять один поисковый запрос (вектор из 384 чисел) и сравнить его со всеми тысячами векторов в базе.

* Как подступиться:
    1. Юзер вводит запрос.
    2. База данных делится на равные куски по количеству ядер твоего Ryzen (например, на 8 или 16 частей).
    3. Каждый поток забирает свой кусок массива all_dimensions и считает скалярное произведение (Dot Product) вектора-запроса с векторами базы.
* 
* Формула скалярного произведения (база косинусного сходства):
$A \cdot B = \sum (A_i \times B_i)$
В коде это просто цикл на 384 итерации, который перемножает числа и складывает в sum.
* Что использовать из книги Уильямса:
Используй новые std::jthread из C++20 (они сами вызывают join() при уничтожении) и std::atomic<float> или std::mutex для безопасной записи топ-результатов из разных потоков в единый финальный список.
Шаг 3: Модуль сжатия контекста (Sparse/Heavy-Hitter Filter)
Вот тут начинается твой ML-эксперимент. Представь, что у тебя лимит памяти — база может хранить строго 1000 векторов (аналог фиксированного KV-кэша на 1000 токенов). Ты скармливаешь ей 1001-й вектор. Кого выкинуть?
В стандартных базах выкидывают самый старый вектор (FIFO). Но в продвинутых LLM-архитектурах (типа H2O) вычисляют Heavy Hitters — векторы, которые имеют наибольший «вес внимания» или к которым чаще всего обращаются.

* Как реализовать алгоритм сжатия руками:
Каждый раз, когда твоя многопоточная система считает сходство, для векторов, которые оказались близки к запросу, ты инкрементируешь счётчик в access_counters. То есть вектор «накапливает важность».
Когда лимит превышен, твой алгоритм ищет вектор с минимальным значением в access_counters и заменяет его


оординаты координатами нового вектора.
* Второй уровень сжатия (продвинутый):
Вместо удаления можно применить векторное квантование. Напиши функцию, которая сжимает float (4 байта) в int8_t (1 байт) для векторов с низким приоритетом, уменьшая их точность, но сохраняя в памяти. Это и есть симуляция того, над чем бьются великие умы в трансформерах.

С какого модуля начнешь накидывать структуру? С модели данных или сразу хочешь пул потоков по Уильямсу спроектировать?

1. Как называется вся система в целом?

* Sparse-RAG / Density-Aware Retrieval — «разреженный» или адаптивный RAG. В отличие от стандартного RAG, который тупо копит в памяти терабайты векторов, этот фильтрует и держит только самое важное.
* In-Memory Vector Database with Eviction Policy — векторная база данных в оперативной памяти с политикой вытеснения (выселения) данных.
2. Как называется алгоритм сжатия/выселения контекста (Шаг 3)?
Ты просил напомнить именно эту идею, где считаются обращения к векторам. У неё есть два главных имени — из мира ML и из мира классических баз данных:

* Heavy-Hitters Oracle (H2O) / Streaming Attention (из мира ML) — это как раз то, о чем написал ИИ. Алгоритм H2O [1, 2] был придуман исследователями, чтобы сжимать KV-кэш в трансформерах. Он оставляет в памяти только те токены (векторы), на которые модель чаще всего «обращает внимание» (накапливает веса внимания/частоту запросов), а остальные безжалостно дропает.
* LFU (Least Frequently Used) Cache Eviction (из мира Computer Science) — если убрать модные нейросетевые термины, то твой access_counters — это чистая классическая политика вытеснения кэша LFU (наименее часто используемые). Твой алгоритм ищет элемент с минимальным счетчиком и заменяет его новым.
3. Как называется «Второй уровень сжатия» (из float в int8)?

* Vector Quantization (Квантование векторов) / Product Quantization (PQ) — процесс перевода непрерывных дробных значений (float32, 4 байта) в дискретные целочисленные (int8, 1 байт). Это база того, как работают взро


слые векторные движки вроде FAISS или Milvus, чтобы терабайты эмбеддингов влезали в оперативку серверов.
